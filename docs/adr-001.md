# ADR 001: a small standalone store

Accepted, 9 October 2026. Use Django 5.2 LTS, SQLite, Authlib, plain HTML/CSS/JavaScript and a single app container. SQLite owns containers, physical records, quantities, history, identity bindings, sessions and device pairings. Original photos are immutable files. Browser IndexedDB owns only unsent drafts and local capture receipts. There is no second inventory database or InvenTree synchronisation.

## Practical fit trial

The official public demo reported InvenTree 1.6.0 dev, API 553. Only synthetic blue-square photos and uniquely prefixed test records were used. It resets daily; this is an observed development demo, not a supported release recommendation.

| Trial | Observation |
|---|---|
| Create two tub locations | Both API requests returned 201 |
| Photo-only unnamed board | Part API returned 400: name required |
| Provisional named board with image | 201 |
| Stock with unknown quantity (`null`) | 400: quantity required |
| One explicitly counted stock item | 201 |
| Search provisional name | 200 |
| Move stock to second location | PATCH 200 |
| Enrich part name/description | PATCH 200; identity retained |
| Read stock tracking history | 200 |

InvenTree has useful parts/stock separation, parameters, attachments, history and configurable SSO. A wrapper could invent provisional parts and treat each mixed bag as one stock unit, but it would still need a distinct unknown-quantity concept, photo-first drafts, mobile navigation and pairing. That makes it disproportionate for the initial household tidy workflow. Stash preserves unknown counts and rough descriptions directly. The tradeoff is responsibility for a deliberately smaller inventory system; procurement, BOMs and manufacturing are excluded.

The current MCP plugin announcement describes retrieval of parts, stock and locations, with authentication and rate limiting. It does not establish permission to perform inventory writes; no MCP integration is enabled.

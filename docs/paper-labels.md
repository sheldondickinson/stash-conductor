# Bulk boxes and A4 paper labels

Open **Pack → Create boxes in bulk**. The default **Create 12 boxes and download labels** makes twelve empty inventory boxes and one A4 sheet containing twenty four separate labels. Each box has two adjacent matching labels, for its top and side. Choose 24, 36 or a custom quantity from 1 to 240; the sheet count is shown before creation. Partial sheets contain only the requested labels.

Batch name, initial physical location and intended destination room are optional. Previewed names and numbers are not reserved. Each final box receives the next available `B001` style identifier and a random human given name from the local curated collection. Change any proposed name before saving, or rename a box later. Explicit names are preserved. Automatic names avoid existing trimmed, case insensitive names; a readable numeric suffix handles exhaustion. Existing inventory is not renamed by migration. Packing selections provide an explicit **Name unnamed boxes** action.

Creation commits the batch, its membership, the boxes, names and request receipt together. The browser stores the request ID and exact payload before submission. If the response is lost, reopen **Create boxes in bulk** and resume the same request. Do not clear browser data while an outcome is uncertain. Shared history remains available in **Box batches**, including after signing out. Signing out clears local pending data; check saved batches before starting another request after an uncertain result.

The PDF is a separate read of saved records after creation. A rendering or download error leaves the completed batch intact. Retry **Download A4 labels** from that batch. **Reprint selected boxes** and the A4 action for existing packing selections create no boxes. Search batches by batch name, box code or saved box name. Adding contents or moving a box never removes its original batch membership.

Print on ordinary A4 paper at **actual size or 100%, single sided**. The downloaded PDF has no browser headers or footers. Cut on the light guides, then tape one matching label on the top and one on the side. Avoid folds, glare and tape bubbles over the QR. Scan one physical sample with the intended phone before printing a large run.

The sheet is 210 × 297 mm, with 10 mm outer margins, four columns and six rows. Cells are 47.5 × 46.1667 mm. Each contains the saved name, bold permanent code and a vector QR with a 27 mm total footprint including four modules of quiet zone. Error correction is M. Generation rejects a URL requiring modules below 0.4 mm rather than silently degrading the layout. Fonts are embedded; long names shrink to a minimum size then use an ellipsis. QR clear space is separate from names, cutting guides and the small Room line. Pair order is row major: first box twice, second box twice, then the next row. Names on new reprints reflect current saved names; QR destinations remain unchanged.

Paper labels use the existing permanent `/c/<code>` destination. They allocate no NFC identities and contain no contents, location or credentials. Signed out scans follow normal login and return to the same box. The capture screen shows its saved name and code, with photo, contents and location actions. Both household members can create boxes, read batches and download PDFs. PDFs and APIs require household authentication and are not cached by the service worker.

Brother labels and PNG/SVG exports now always include a saved box name where present. Its private queue, cutter settings, tape dimensions and uncertainty rules are retained. Paper labels need neither a Brother printer nor NFC hardware. The station firmware is unchanged.

## Implementation and validation

SQLite IMMEDIATE write transactions serialise the allocation, existing manual code creation, tag creation and rename operations. A durable number sequence and unique code reservations prevent reuse, including after future archival workflows. The batch request UUID is unique in the database; actor, request digest and existing receipt checks reject conflicting reuse. The additive migration seeds only the allocator from existing identifiers and leaves names, contents and URLs untouched.

Focused tests cover 1, 11, 12, 13 and 24 boxes, invalid quantities, shared permissions, replay, renderer failure, name exhaustion, single and scanned creation, existing duplicates, reprints and tape QR decoding. Separate disk database HTTP checks exercise simultaneous household allocation and duplicate submission. Sample PDFs are made only from disposable records; they are not household box labels. Rendered pages and partial last pages are visually inspected and every QR is independently decoded at 300 dpi. Browser checks cover response loss across reload, PDF failure/retry, phone and desktop widths, enlarged text and reduced motion. Physical paper printing and iPhone scanning remain separate acceptance checks.

The PDF renderer uses pinned [ReportLab](https://docs.reportlab.com/reportlab/userguide/ch2_graphics/) and the existing QR library. The embedded bold face is the Bitstream Vera font supplied with ReportLab under its included licence; the existing DejaVu label font and licence are retained.
